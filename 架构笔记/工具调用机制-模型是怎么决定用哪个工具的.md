# 工具调用机制：模型是怎么"决定"用哪个工具的

> 🔧 **注意定位：这篇不是 Pi 的架构结论，是"模型侧元认知"——一个在 Claude Code 宿主里运行的模型，对自己"怎么决定调用工具"的自我观察。**
> Pi 源码里能证明的只有协议层（§8 实证）：模型输出 toolCall → Pi 执行 → 结果回填 → 循环。"模型凭什么选这个工具、工具使用是不是训练出来的"是通用业界认知 + Claude Code 宿主下的观察，**Pi 源码推导不出**。
> 配套阅读：[运行时与队列架构.md](运行时与队列架构.md)（Agent 怎么跑）、[v2演进动机.md](v2演进动机-开发者为什么这样迭代.md)（为什么这么跑）。

---

## 0. 一句话结论

**工具调用不是"检索到工具"，也不是某个 `if` 语句，而是模型做条件概率抽样。** 上下文里有没有这个工具、该不该用、用哪个、参数填什么——**全部是 token 预测**。决策拆成四层链条：宿主定候选池 → 模型选哪个 → 宿主+用户给执行权 → 训练决定能力来源。

---

## 1. 先纠正前提：工具不是模型"自带"的

最常见的误解："AI 会上网" = AI 本身会冲浪。不对。

- 模型本身**没有任何工具**，只有一套"函数调用"的能力（能输出工具调用格式、能读结果）。
- **工具清单是宿主（运行我的 CLI/环境）配置注入的**。宿主决定我面前摆哪些工具。
- 同一模型换宿主/配置，工具可以完全不同——"我会不会上网"取决于环境，不取决于我。

工具来源分两类，机制一样，来源不同：

| 类型 | 例子 | 来源 |
|---|---|---|
| 宿主内置工具 | `Read` / `Bash` / `WebSearch` | 宿主自己实现，直接进函数列表 |
| MCP 工具 | `mcp_router__fetch` / `web_search_prime` | 宿主连的 MCP 服务器注册进来 |

---

## 2. 工具清单是什么（输入组装，由宿主决定）

我"看到"的工具清单**不是一个可检索的数据库，就是一段文本**，塞进我的上下文，和你的问题地位相同——都是"要预测的下文的前置内容"：

```
[系统提示] 你可以使用以下工具：
  WebSearch(query: string)    ← "Search the web. Returns result blocks."
  Read(file_path: string)      ← "Read a file from the local filesystem."
  Bash(command: string)        ← "Execute a bash command."
  ...
[用户消息] 别人说有个 RLM 是吗？
```

这一步**决定的是"有哪些候选"**。WebSearch 会不会出现在这里，是宿主的事，不是我的事。

## 3. "命中"的真相：是补全，不是扫描

我内部没有在做"关键词匹配检索"。我看到的是：工具名+描述+参数格式的文字 + 你的问题。然后我干一件事——**预测最合理的下一个 token 序列**。

"扫一眼清单命中"的真实机制是三股力量：

1. **配对模式**（训练数据）：海量"任务描述 → 该调的工具"的例子，让模型学会"要外部事实 → 对应 WebSearch 这种描述"。
2. **RL 强化**（训练过程）：专门训练"在合适时机调工具、传对参数、别瞎调"，调错了会被降权。工具使用是 RL 重点练过的技能。
3. **语义相似性**（表征空间）：工具描述里的 "web search" 和问题里的"这词是啥"，在模型内部表征上离得近 → 权重指向该工具。

> 关键：**没有检索，只有补全**。模型不是"找到"WebSearch，是"预测到该写 `WebSearch(...)` 这几个字"。

## 4. 谁决定调用：四层决策链

问"究竟谁决定调用 WebSearch"，答案是**没有单一主体，是一条四段链条**：

```
你问"RLM 是啥"
     │
     ▼
① 输入组装 ─── 宿主决定：面前有哪些候选工具（工具清单里【有】WebSearch）
     │
     ▼
② 决策点 ─── 模型决定：token 概率抽样，选哪个
     │   （对上下文做预测，候选续写带概率：
     │     直接回答 20% | WebSearch(...) 55% | Bash(...) 5% | 让你去查 8% ...）
     │     → 采样 → 生成 WebSearch 调用）
     ▼
③ 执行关卡 ─── 宿主 + 你决定：permission 拦截，授权才真的出网
     │
     ▼
④ 能力来源 ─── 训练 + RL 决定：为什么我会"往这个方向抽"
     │
     ▼
    WebSearch 真的发请求 → 结果回填 → 我读结果回答
```

| 层 | 决定什么 | 谁决定 | 性质 |
|---|---|---|---|
| ① 候选池 | 面前**有哪些**工具 | 宿主 | 确定性（配置） |
| ② 选哪个 | **该不该用、用哪个** | 模型 | **概率抽样** |
| ③ 执行权 | **能不能真的跑** | 宿主 + 用户授权 | 确定性（权限） |
| ④ 能力来源 | 为什么往这个方向抽 | 训练 + RL | 学来的偏好 |

**三个性质必须记牢**：
- ② 不是 if 语句：没有任何代码写"`if (用户问RLM) use WebSearch`"。
- ② 不是"自由意志"：我"倾向查证"是 RL 把"事实不确定就该查"强化成了高概率。
- ② 不是 100%：那 55% 不是 100%，有时模型会选"直接回答"——然后一本正经编错。

## 5. token 级的调用过程：每一步都是条件概率

**token 不是词，是词的子片段**（`WebSearch` 可能切成 2~3 个 token）。一次工具调用，真实输出是一长串 token **一环一环被预测出来**——每一步：给定前面已经写完的所有 token，预测下一个。

那次真实调用（去掉包装后的真身）：

```
<tool_call> WebSearch(query="RLM Reasoning Language Model 是什么 与 LLM 区别") </tool_call>
```

| 步 | 我已写下的 token 序列 | 我在预测下一个 | 那一刻的概率（示意） |
|---|---|---|---|
| 1 | `(开头)` | `<tool_call>` vs 直接回答 | 55% vs 20% ← **决策就在这一抽** |
| 2 | `<tool_call>` | `WebSearch` vs `Bash` vs `Read` | 60% vs 15% vs 8% |
| 3 | `...WebSearch` | `(` vs `[` vs 结束 | 70% |
| 4 | `...WebSearch(` | `query` vs `url` | 80% |
| 5 | `...query=` | `"` | 95% |
| 6 | `...query="` | `RLM` vs `什么是` … | 多个候选 |
| 7+ | …继续 | 直到拼完整个 query 串 | … |

**三个真相**：
- **决策"用不用工具"只在第 1 步抽一次**，后面全是"既然用了，就得把参数填完"的惯性续写。55% 承载了整个决策，后面几十个 token 只是执行它。
- **参数内容也是预测出来的**——不是查表，是"根据上下文，最合理的提问是什么"的一个个 token 抽样。query 串可能拼出不一样的。
- **中间还有 `<tool_call>` 开闭标记、参数名、引号、换行**，上百个 token，真身比压缩版长得多。

## 6. 为什么生成"这个"具体调用

生成"这个"不是随机的——三个条件叠加后概率最高的样本。

### 6.1 为什么是 WebSearch 不是别的工具

| 事实（我当时上下文） | 效果 |
|---|---|
| 代码库我刚 grep 过、零命中 | Read / Grep / Bash 这些"查内部"的工具概率暴跌 |
| 我**没有**目标 URL | WebFetch（需要具体网址）概率低 |
| 工具描述写着 "Search the web" | 和"用关键词找外部事实"完全匹配 |

一句话：**别的路都堵死了，WebSearch 是唯一开口**。

### 6.2 为什么 query 串是这一句——逐段拆

```
WebSearch(query="RLM Reasoning Language Model 是什么 与 LLM 区别")
                 └──┬──┘ └─────────┬─────────┘ └─┬─┘ └────┬────┘
                    ①         ②              ③       ④
```

| 段 | 内容 | 为什么存在 |
|---|---|---|
| ① | `RLM` | 核心术语，检索必有 |
| ② | `Reasoning Language Model` | **我怀疑的展开**。拼进去让搜索引擎精确命中 arXiv 论文/维基，避免 RLM 被错解成别的缩写 |
| ③ | `是什么` | 意图词：我要"定义" |
| ④ | `与 LLM 区别` | 意图维度：语境基准是 LLM，我想搞清两者边界 |

**中英混写是召回策略**（训练学来的）：英文全称命中权威源，中文意图词命中中文解读，两头都要。

> ② 那句 "Reasoning Language Model" 不是查来的，是我**赌**的——"RLM" 最可能的展开。这次赌对了：真的搜到了那张蓝图。

### 6.3 诚实的边界

换个采样时刻，可能生成 `what is RLM vs LLM` 或 `RLM 推理语言模型`。这串**不是唯一解**，是当时条件概率下的一个合理样本。**工具调用没有"背答案"，只有"根据上下文赌最合理的下一个词"。**

## 7. 与 RLM 的关系：哪些是业界认知，哪些是 Pi 可证

⚠️ **这里必须拆开——上一条（§0-6）里"工具使用是训练出来的"这个结论，来源是通用业界认知 + 我在 Claude Code 下的自我观察，不是 Pi 源码推导的。** 对 Pi 只能下到下面这种程度：

- **业界认知（通用，非 Pi 结论）**：新一代 RLM（o1 / DeepSeek-R1 / Claude 5 一族）把"该不该调工具、传啥参数、调完怎么用结果"作为 RL 重点训练的第一性能力。这是 arXiv/技术博客层面的共识，任何代码库都证明不了，Pi 也一样。
- **Pi 可证的（源码/配置层面）**：Pi 的设计**支持** RLM 时代——`packages/ai/src/api/anthropic-messages.ts` 的 `thinkingEnabled` / `thinkingBudgetTokens` / `thinkingLevel`（off/low/medium/high/xhigh，"adaptive thinking models"）。这说明 Pi 能把"思考旋钮"传给模型，但**这只证明 Pi 兼容 RLM 模型，证明不了"工具使用是训练出来的"**。
- **Pi 真正能证明的协议**：见 §8——模型输出 toolCall 后，Pi 的 `agent-loop` 负责过滤、执行、回填、循环。**"模型凭什么选这个工具"这一层，在 Pi 源码里是缺席的**（§8 的测试里它是被 mock 掉的）。

一句话：**本文 §0-6 的机制是"模型侧"的，属于 Claude Code 宿主观察；Pi 侧只有协议层（§8）是源码可证的。**

## 8. Pi 源码实证：工具调用协议真实长什么样（用 Pi 跑出来的）

> ✅ 本节的结论全部来自真实运行的 Pi 测试：`packages/agent/test/agent-loop.test.ts`（12 个 tool 用例通过）。它证明了 **Pi 侧工具调用的完整协议**——这是本文唯一能从 Pi 源码得出的硬结论。

### 8.1 Pi 侧协议（agent-loop.ts，可证的硬逻辑）

```
模型输出（streamFn）──► assistantMessage.content
                          │
                          ▼
  agent-loop.ts:203  content.filter(c => c.type === "toolCall")   ← 只认 toolCall 这一种标记
                          │
                          ▼
  agent-loop.ts:214  executeToolCalls(...)                        ← 顺序/并行执行
                          │   (toolCall.name → 在 context.tools 里找同名工具)
                          ▼
  工具 execute() 跑完 ──► createToolResultMessage()               ← 结果包成 toolResult 消息
                          │
                          ▼
  agent-loop.ts:219  currentContext.messages.push(result)         ← 回填上下文
                          │
                          ▼
  hasMoreToolCalls 为真 → 继续下一轮 LLM；否则 turn_end
```

代码证据：`agent-loop.ts:203`（过滤 toolCall）、`:418-426`（顺序/并行分派）、`:607`（按名查工具 `context.tools?.find`）、`:218-221`（结果回填）。

### 8.2 关键发现："模型为什么选这个工具"在 Pi 源码里是缺席的

测试 `agent-loop.test.ts:327-345` 里，模型侧完全是 **mock 的**：

```ts
if (callIndex === 0) {
    // First call: return tool call  ← 人为塞一条 toolCall
    const message = createAssistantMessage(
        [{ type: "toolCall", id: "tool-1", name: "echo", arguments: { value: "hello" } }],
        "toolUse",
    );
    stream.push({ type: "done", reason: "toolUse", message });
}
```

**Pi 把"模型输出 toolCall"当作既成事实（外部输入），自己只负责"收到就执行、回填、循环"。** 没有任何一行代码回答"模型凭什么决定调 echo 而不是别的"——那个决定在模型侧，Pi 接不住也管不着。

### 8.3 回到用户的批评

我原文档 §0-6 用"四层决策链 / token 级抽样"讲的决定机制，是 **Claude Code 宿主**里运行的模型对自己行为的观察，不是 Pi 的实现。Pi 的实现只覆盖了 §8.1 这一条协议。两边的分工：

| 问题 | Claude Code 宿主观察（§2-6） | Pi 源码实证（§8） |
|---|---|---|
| 工具清单从哪来 | 宿主注入文本 | 测试里直接放 `context.tools: [tool]` |
| 谁决定"选哪个工具" | 模型（Claude Code 里的我） | **缺席**（mock 塞入） |
| 谁决定"能不能执行" | 宿主 permission 关卡 | 无权限层，收到就执行（harness 有 `beforeToolCall` 钩子可外挂） |
| 执行后怎么办 | 结果回填再续 | 回填 `messages` 再 `hasMoreToolCalls` 循环 |

## 9. 可靠性与局限（诚实清单）

1. **概率行为**：可能选错工具、传错参数。permission 关卡 + retry 是宿主的安全网。
2. **我的知识有截止点**：2025-2026 才热起来的术语（如 RLM），必须查而非凭记忆——这是"该不该调 WebSearch"的触发规则。
3. **搜索本身有局限**：WebSearch 是 US 区域；结果质量取决于搜索引擎；返回的摘要需要我判断可信度。
4. **token 精确切分不可回放**：具体切几个 token 取决于分词器词表，只能给结构近似，不能逐字节录音。
