# v2 演进动机：开发者为什么知道要这样迭代

> 🔧 源码溯源 · 基于 harness.md 设计文档原文 + git 提交历史（73414d08b → 2e4d23959）。
> 本文回答一个"代码看不出来"的问题：开发者凭什么知道要把架构演进成 records + reducer + manual 驱动？答案是——**不是预知，是被 bug 逼的**。

---

## 0. 一句话结论

**开发者不是"知道"要这样迭代，是"被 bug 推着"一步步迭代的。** 每次演进都源于一个具体的、切肤的崩溃/恢复问题。而且整个演进遵循同一套方法论循环，不是灵光一现。

---

## 1. 动机起点：crash mid-tool 这个梦魇

harness.md 开篇 Part 0.5 用一整节描述场景：**"工具跑到一半，电脑崩溃了"**。这是 v2 全部设计的出发点。

### 旧架构（73414d08b）的痛点

你之前学过的旧版就是这个双实现版本：

```
旧 AgentHarness（一个胖类，状态全在内存里）
   ├─ 队列（steer/followUp）→ 内存数组
   ├─ turn state / phase → 内存字段
   └─ 持久化 → "额外附加"（定时写盘，可能过时）
```

崩溃 = 内存全丢。恢复只能靠"把消息重放一遍让 LLM 重新跑"。但工具可能已产生副作用（写文件、发请求）——重放会导致**工具跑两遍**。

### 开发者遇到的具体 bug（git 提交可见，2026-08-02 起）

```
01eeafd14 docs: add durable queue-item cancellation      ← 队列项崩溃后消失/重复
32850ef7c fix: resume after context-limited length stops  ← length 截断后恢复失败
a5953d2e1 feat: validate harness recovery record logs     ← 恢复日志不合法导致错乱
```

---

## 2. 应对方法：把"易错的状态"从内存挪进"不易错的日志"

面对"崩溃后状态对不上"，开发者的关键判断是：

> **与其修 bug，不如让状态根本不可能错。**

这就是所有迭代方向的总纲：

```
旧心智：状态在内存里，持久化是"额外附加"（可能过时）
新心智：状态在日志里，内存只是"临时副本"（日志是唯一真相）
```

### 三条落地原则（harness.md §0.3 白纸黑字）

**① 三条存储，一个不变量**

> 每个东西要么是 entry（会话树）、要么是 register（当前状态）、要么进 ledger（用量记录）。没有第三个去处。

**② 原子事务**

> 一组写入要么全部生效、要么全不生效。崩溃只可能发生在事务之间，绝不可能在事务中间。

→ 这让"崩溃状态可枚举"：只需要知道"上一个完成的事务"，不需要猜。

**③ 持久化的程序计数器**

> 每步结束，把完整的操作状态覆写进一个 register（`op.state`）。恢复时**不重放日志、不从"缺了啥"猜位置**，直接读那个寄存器。

---

## 3. 为什么"必然"会走到 records + reducer

开发者 §1.8 "Why write-once plus registers" 里的理由，全是权衡后的必然：

| 设计决策 | 开发者原话 | 解决什么 |
|---|---|---|
| write-once + registers | "Recovery is a read. Five register point-lookups... **No reducer exists to have a bug.**" | 恢复 = 5 次点查，没有中间逻辑可错 |
| 崩溃状态可枚举 | "Crash states are enumerable. Between transactions, never inside one." | 不用猜"走到哪了" |
| 清理 = 删除，不是回收 | "A 30-turn run overwrites one register ~30 times and then deletes it. **Nothing to collect.**" | 没有垃圾要 GC |
| 不做 repair-by-rewrite | "interrupt it and rerun it and you get **the same result**." | 恢复可重复、可测试 |
| 并发 trivial | "Readers never see partial state; **there is nothing to lock.**" | 不靠锁，靠不变式 |

### 关键自指：reducer 是过渡品

注意 "No reducer exists to have a bug"——这句特别妙。开发者知道 reducer 本身可能写错，所以**目标设计是连 reducer 都不需要**（5 次寄存器点查就行）。

你看到的 `reducer.ts` 是**过渡期产物**：因为当前 records 模型还没完全变成寄存器模型，所以先用 reducer 从 records 重建状态。**最终形态是消灭 reducer，不是保留它。**

---

## 4. reducer 和 manual 驱动从哪来

它们是同一个方法论的推论：

```
崩溃恢复难测 → 需要"能精确控制每一步"的执行方式 → manual 驱动
               （manual 模式停泊时零副作用，可测试任意竞态）
恢复不可靠  → 需要"纯函数、可独立验证"的状态重建 → reducer
               （validateRecordLog 保证只有合法日志能进 reducer）
```

### git 历史验证脉络（时间倒序）

```
8-05  feat: validate harness recovery record logs      ← reducer 的校验层
8-05  feat: add indexed harness recovery queries        ← 恢复查询
8-04  feat: implement harness v2 for in-memory storage  ← v2 首次落地
8-02  docs: split harness v2 into effects/generator     ← 先写设计文档再写码
8-02  docs: add durable queue-item cancellation         ← 从队列 bug 起笔
```

**注意提交顺序**：`docs:` 开头的设计提交**先于** `feat:` 实现提交。开发者**先写设计文档（把"为什么"想清楚）→ 再写代码**。

---

## 5. 方法论循环：完整的迭代公式

```
1. 遇到具体 bug（崩溃后队列丢/重、length 截断恢复失败）
   ↓
2. 问"怎么让这类 bug 不可能发生"而不是"修这一个"
   ↓
3. 得出设计原则（日志为真相 / 原子事务 / 程序计数器）
   ↓
4. 先写设计文档，把每个权衡的"为什么"写下来
   ↓
5. 实现时按原则走，bug 确实消失了
   ↓
6. 下一个 bug 出现 → 回到 1（这次会更深）
```

**最反直觉的一点**：开发者不是"预知"了 records/reducer/manual 这套终局。他们是**一步步被 bug 推着**，每解决一层，下一层的问题才浮现。reducer 甚至是个"注定要被消灭"的过渡品——如果寄存器模型完整落地，reducer 就删掉了。

---

## 6. 给你的启发

架构迭代不是天才的预测，是**痛苦的渐进**。可复用的三条：

1. **bug 要追到设计根因**：别修"这一个"，问"怎么让这类 bug 不可能发生"
2. **设计文档先于代码**：把权衡的"为什么"写下来，代码只是执行
3. **中间产物注定被消灭**：reducer 这种过渡品不丢人，它是走向终局的桥
